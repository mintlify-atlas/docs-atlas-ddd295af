---
title: "Secrets Management"
description: "How Airbyte handles and obfuscates credentials, and how to configure external secrets managers."
---

Airbyte stores secrets in the configured secret persistence layer as sources and destinations are created. By default, secrets are stored as encrypted Kubernetes secrets on your cluster. You can optionally use an external secret manager.

## How Airbyte handles secrets

Airbyte stores configuration for internal models as JSON blobs in the database. Connector specs declare sensitive fields with `"airbyte_secret": true`. Airbyte uses this property to identify which fields must be treated as secrets.

A secret field:

- Must not be returned by the API.
- Must not be printed in logs.
- **Must be obfuscated in the stored JSON blob and the UI.**

<Tip>
  It is possible to deploy Airbyte so that users with deployment access do not have secret access. This increases deployment flexibility and supports least-privilege security models.
</Tip>

## Secret obfuscation

When a secret is stored, Airbyte:

1. Generates a deterministic coordinate of the form:
   ```
   <airbyte-workspace>_<workspace-id>_secret_<uuid>_<version>
   ```
   Example:
   ```
   airbyte_workspace_024eaa40-75ae-4014-941d-b9e938c3a363_secret_5675437d-ea6b-4f9a-9a0c-d76066004841_v1
   ```

2. Writes the original secret payload to that coordinate in the secret store.

3. Replaces the secret field in the stored JSON with an object referencing the coordinate.

**Example:** Given a connector spec with an `api_token` secret field:

```json
// Raw input
{
  "email": "user@example.com",
  "api_token": "fake-token"
}
```

Airbyte stores:

```json
{
  "email": "user@example.com",
  "api_token": {
    "_secret": "airbyte_workspace_4e7d7911-0307-40fe-9b79-f00c0dfbb082_secret_d66baab6-3c8d-4ae5-91a6-ca8d904c4780_v1"
  }
}
```

When a connector operation runs, Airbyte reads the obfuscated JSON, extracts the secret coordinate, and hydrates the correct value before passing it to the connector.

## Operational details

- When configuration is updated, Airbyte **increments the version** of the secret coordinate while preserving the prefix (e.g. `_v1` → `_v2`). This lets operators understand how often a secret has been modified.
- The workspace ID in the coordinate allows operators to identify which workspace owns a secret.
- Secrets created during `Discover` or `Check` operations that cannot be associated with a workspace use `00000000-0000-0000-0000-000000000000` as the workspace ID. Airbyte attempts to expire these after 2 hours.
- As of Airbyte 0.63.10, old secrets are deleted when connector configuration is updated or deleted.

## External secrets managers

For Self-Managed Enterprise deployments, you can configure an external secrets manager. All connector secrets (OAuth tokens, database passwords, etc.) are written to and read from the external manager.

<Warning>
  Changing the connector secret storage configuration after initial setup will cause all existing connectors to fail. You will need to recreate them.
</Warning>

<Tabs>
  <Tab title="AWS Secrets Manager">
    Add to `values.yaml`:

    ```yaml title="values.yaml"
    global:
      secretsManager:
        enabled: true
        type: AWS_SECRET_MANAGER
        secretName: "airbyte-config-secrets"
        awsSecretManager:
          region: us-east-1
          authenticationType: credentials  # or "instanceProfile"
          tags:
            - key: team
              value: deployments
          kms:  # Optional: ARN for KMS decryption
    ```

    Set `authenticationType` to `instanceProfile` if your EKS cluster has an IAM role with the required permissions.

    Required IAM permissions:

    ```json
    {
      "Effect": "Allow",
      "Action": [
        "secretsmanager:GetSecretValue",
        "secretsmanager:CreateSecret",
        "secretsmanager:ListSecrets",
        "secretsmanager:DescribeSecret",
        "secretsmanager:TagResource",
        "secretsmanager:UpdateSecret"
      ],
      "Resource": ["*"]
    }
    ```
  </Tab>

  <Tab title="GCP Secret Manager">
    Add to `values.yaml`:

    ```yaml title="values.yaml"
    global:
      secretsManager:
        enabled: true
        type: GOOGLE_SECRET_MANAGER
        secretName: gcp-cred-secrets
        googleSecretManager:
          projectId: your-gcp-project-id
          credentialsSecretKey: gcp.json
    ```

    Create a Kubernetes secret containing your GCP credentials:

    ```bash
    kubectl create secret generic gcp-cred-secrets \
      --from-file=gcp.json \
      --namespace airbyte
    ```
  </Tab>

  <Tab title="HashiCorp Vault">
    Configure via environment variables (alpha support):

    ```
    SECRET_PERSISTENCE=VAULT
    VAULT_ADDRESS=https://vault.example.com
    VAULT_PREFIX=kv/airbyte/
    VAULT_AUTH_TOKEN=<your-token>
    VAULT_AUTH_METHOD=token
    ```

    Only token-based authentication is currently supported.
  </Tab>

  <Tab title="Azure Key Vault">
    Add to `values.yaml`:

    ```yaml title="values.yaml"
    global:
      secretsManager:
        enabled: true
        type: AZURE_KEY_VAULT
        secretName: "airbyte-config-secrets"
        azureKeyVault:
          tenantId: "your-tenant-id"
          vaultUrl: "https://your-vault.vault.azure.net/"
          clientId: ""
          clientIdSecretKey: ""
          clientSecret: ""
          clientSecretSecretKey: ""
    ```

    Airbyte requires the **Key Vault Secrets Officer** built-in role (or equivalent permissions to read and write secrets).
  </Tab>
</Tabs>
