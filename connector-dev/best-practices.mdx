Connectors that follow these guidelines earn the **Airbyte Certified** label, indicating they pass a high quality bar and perform reliably in production. Following them is not required for a contribution to be accepted, but doing so is strongly recommended.

## Core principles

1. **Reliability and usability over features.** One connector that works reliably is better than two that are unreliable. Support one feature well before adding a second.
2. **Fail fast.** Users should not be able to configure something that will not work. Validate inputs upfront.
3. **Fail actionably.** If something goes wrong, give the user a clear message about what they can do to fix it.

## Connection check

The `check` operation should verify permissions upfront, not just confirm the API is reachable.

<Tabs>
  <Tab title="Bad">
    ```python
    def check_connection(self, logger, config):
        try:
            requests.get("https://api.example.com/ping")
            return True, None
        except Exception as e:
            return False, str(e)
    ```
    This tells the user the API is reachable, but not whether their credentials are valid.
  </Tab>
  <Tab title="Good">
    ```python
    def check_connection(self, logger, config):
        try:
            response = requests.get(
                "https://api.example.com/v1/me",
                headers={"Authorization": f"Bearer {config['api_key']}"}
            )
            if response.status_code == 401:
                return False, "Invalid API key. Please verify your credentials."
            response.raise_for_status()
            return True, None
        except requests.exceptions.ConnectionError:
            return False, (
                "Unable to reach api.example.com. "
                "Check your network connection and firewall rules."
            )
    ```
  </Tab>
</Tabs>

### Actionable error messages

| Bad | Good |
| --- | --- |
| "Can't connect" | "Unable to reach the host. Verify there are no firewall rules blocking Airbyte." |
| "Invalid credentials" | "Your username/password combination is incorrect. Please verify your credentials." |
| "403 Forbidden" | "The API token does not have permission to read the 'orders' resource." |

## Error handling and retries

Most APIs enforce rate limits. Your connector must handle HTTP 429 responses gracefully rather than failing.

The Python CDK retries automatically with exponential backoff on 429 and 5xx responses. Customize the behavior when the API provides retry hints:

```python
def backoff_time(self, response: requests.Response) -> Optional[float]:
    """Use the Retry-After header if the API provides it."""
    retry_after = response.headers.get("Retry-After")
    if retry_after:
        return float(retry_after)
    return None

def should_retry(self, response: requests.Response) -> bool:
    return response.status_code in (429, 500, 502, 503, 504)
```

<Warning>
Airbyte always tries to make requests as fast as possible. It does not preemptively rate-limit. Only slow down when the API signals that you should (429 or headers like `X-RateLimit-Remaining: 0`).
</Warning>

## Incremental sync

Implement incremental sync wherever the API supports it. Syncing all records on every run places unnecessary load on the API and the destination.

- Use the smallest reliable cursor unit. A `updated_at` timestamp is more precise than a date-only field.
- Consider a **lookback window** if the API can update records without changing their cursor field.
- Use stream slices to checkpoint state frequently. If a sync of 10 000 records fails at record 9 000, the next attempt should resume from the checkpoint, not from the beginning.

```python
# Checkpoint every 100 records
state_checkpoint_interval = 100
```

## Schema design

- Declare a JSON Schema for every stream. Do not emit records without a schema.
- Mark secret fields with `"airbyte_secret": true` in the spec. Acceptance tests fail if fields named `api_key`, `password`, `client_secret`, etc. are not marked as secrets.
- Use `"format": "date-time"` for ISO 8601 datetime fields and `"format": "date"` for date-only fields. Destinations use these hints to choose the right column type.
- Define `primary_key` on streams where records have a unique identifier. This enables deduplication in append+deduped sync mode.

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "properties": {
    "id": { "type": "integer" },
    "email": { "type": "string", "format": "email" },
    "created_at": { "type": "string", "format": "date-time" },
    "amount": { "type": "number" }
  }
}
```

## Progress logging

Emit a log message at least every 5 minutes so users can confirm the sync is still running. Long silences cause uncertainty and unnecessary support requests.

```python
def read_records(self, sync_mode, stream_slice=None, stream_state=None, **kwargs):
    count = 0
    for record in self._fetch_records(stream_slice):
        count += 1
        if count % 1000 == 0:
            self.logger.info(f"Read {count} records from {self.name}")
        yield record
```

## Breaking changes

When you publish a new version of a connector, the following changes are **breaking** and require a major version bump and a migration guide:

| Change | Reason |
| --- | --- |
| Removing a field from a stream's schema | Destinations may have columns that reference the removed field |
| Changing a field's data type | Destination column types may not be compatible with the new type |
| Renaming a field or stream | Existing connections reference the old name |
| Changing the cursor field for an incremental stream | Existing state is no longer valid |
| Removing or renaming configuration options | Existing source configurations break |
| Changing the authentication mechanism incompatibly | Users must re-authenticate |

Document breaking changes in `metadata.yaml` under `releases.breakingChanges`:

```yaml
releases:
  breakingChanges:
    2.0.0:
      message: >
        The `created_date` field on the `orders` stream has been renamed to
        `created_at` to match ISO 8601 conventions. Reset the `orders` stream
        after upgrading.
      upgradeDeadline: "2024-03-01"
```

## Testing checklist

Before submitting a connector:

- [ ] All streams return records during `basic_read` acceptance tests
- [ ] `check` returns a helpful error message for invalid credentials
- [ ] Incremental sync is implemented for all streams that support it
- [ ] Rate limit responses (429) are handled without failing the sync
- [ ] Schema accurately describes the records output by the connector
- [ ] Secret fields in the spec are marked `"airbyte_secret": true`
- [ ] Unit tests cover edge cases not covered by acceptance tests
